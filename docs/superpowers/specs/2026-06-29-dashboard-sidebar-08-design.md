# Dashboard Sidebar-08 Design

## Goal

Replace Pandar's current dashboard shell with the shadcn `sidebar-08` application sidebar and reorganize the authenticated dashboard into four operator pages: Devices, Agents, Users, and Settings. The user-facing authenticated area must include Logout support.

## Scope

In scope:

- Initialize shadcn for the root `frontend/` Next.js app if needed.
- Run the shadcn sidebar block installation from `frontend/` using `npx shadcn@latest add sidebar-08` or the equivalent registry-qualified command reported by shadcn tooling.
- Run shadcn only from `/home/indexyz/pandar/frontend`. Do not target `frontend/auth`, which has its own independent `components.json`. Inspect generated files after install and adapt the sidebar block into Pandar's app shell rather than blindly accepting sample route/page overwrites.
- Ensure shadcn-generated `@/` imports resolve in the root frontend build by updating `frontend/tsconfig.json` aliases or by converting generated imports to the repo's existing relative import style.
- Replace the current dashboard header, sticky section nav, and single-page dashboard composition with a sidebar-08 style app shell.
- Add dashboard routes or route-backed views for:
  - `Devices`: fleet health, attention summary, printer inventory, job history, dispatch, and recovery controls.
  - `Agents`: linked agents and diagnostics related to agent/printer command state.
  - `Users`: tenant user administration, join links, and a visible Logout action.
  - `Settings`: tenant/runtime settings, tenant tokens, agent pairing, live status, notifications, and audit activity.
- Preserve existing API calls, tenant selection behavior, auth redirects, live printer event handling, admin actions, and localization support.
- Update `docs/roadmap.md` after code changes.
- Add focused smoke coverage that fails before the dashboard shell/view mapping exists and passes after implementation.

Out of scope:

- Backend API changes.
- New persistent data, migrations, or database queries.
- Reworking authentication providers beyond exposing the existing sign-out URL/action.
- Replacing all existing dashboard domain components with new data visualizations.
- Adding new product features beyond the four-page dashboard reorganization and logout affordance.

## Current Context

The root dashboard is currently implemented in `frontend/app/page.tsx` and `frontend/app/dashboard-runtime.tsx`. It fetches all tenant-scoped data server-side, then renders a single client dashboard with a custom header, sticky section nav, fleet status, printer inventory, jobs, dispatch, recovery, diagnostics, runtime status, tenant settings, and tenant admin controls.

The existing auth provider config already exposes `signOutUrl` for Clerk, Logto, and Better Auth via `frontend/app/auth-provider.ts`. Better Auth sign-out cookie clearing is implemented under `frontend/app/auth/betterauth/sign-out/route.ts`. The implementation should reuse these paths rather than inventing a new logout backend.

The design system requires a calm, technical operations console: restrained slate surfaces, cyan/teal accent only for action/selection/state, no decorative marketing layout, and standard product navigation patterns.

## Design

The dashboard becomes a route-backed app shell:

- Shared server data loading stays centralized so the four pages use the same tenant/auth/fetch logic as the current dashboard.
- A new shared dashboard route component accepts a `view` value and passes all loaded data into the client runtime.
- `/` redirects to `/agents` when `command` is present and `/devices` otherwise, while preserving dashboard query parameters currently used by the app: `tenant`, `command`, and `status`.
- `/devices`, `/agents`, `/users`, and `/settings` render the same sidebar app shell with the matching active navigation item.
- The sidebar uses the shadcn sidebar block/component vocabulary generated by `sidebar-08`, adapted to Pandar labels and routes.
- Existing server actions or links that currently return to `/?tenant=...&status=...` or `/?tenant=...&command=...` must continue to surface their feedback after the redirect. Root redirect logic may route those queries to the relevant page, or action redirects may be updated directly when the mapping is explicit.

The client runtime keeps the current WebSocket/live event behavior, but renders page-specific content:

- Devices shows operational state for printers/jobs: fleet status, attention items, inventory, job history, dispatch, and recovery.
- Agents shows linked agent inventory and diagnostics.
- Users shows tenant users, identities, join links, and logout. Admin token and agent pairing controls are not placed here unless they directly support user access.
- Settings shows tenant/runtime/auth details, token management, pairing controls, live notifications, and audit events.

If no tenant is available after external auth, the existing onboarding panel remains unchanged.

Route behavior:

- Auth redirect checks currently in `frontend/app/page.tsx` must run before every dashboard view renders, including `/devices`, `/agents`, `/users`, and `/settings`.
- External-auth onboarding remains a dashboard route outcome: if `meResult.data` exists and the user has no tenants, the shared route component renders `OnboardingPanel` instead of the sidebar shell for the requested dashboard view.
- Root `/` redirect target is `/agents` when `command` is present, because command results render in diagnostics; otherwise it is `/devices`. Preserve `tenant`, `command`, and `status` query parameters in the redirect target.
- `status` action feedback renders in the shared shell header area for any dashboard view that receives a `status` query parameter. Existing dispatch/upload redirects can continue to use `/` and will land on `/devices?tenant=...&status=...` unless an action is explicitly remapped to a more relevant view.
- Query preservation is exact:
  - Root redirect preserves `tenant`, `command`, and `status`; it targets `/agents` when `command` is present and `/devices` otherwise.
  - Normal sidebar navigation preserves only `tenant`; it drops transient `command` and `status` feedback.
  - Tenant switching preserves the current dashboard view and preserves `status`, but preserves `command` only on `/agents`; switching tenants on `/devices`, `/users`, or `/settings` drops `command`.
  - Action feedback URLs preserve `tenant` and `status`; command-result URLs preserve `tenant` and `command` and target `/agents` directly or through root redirect.
- Export the route/view contract, root redirect target builder, tenant switch URL builder, and logout href selector as importable pure functions so `frontend/app/dashboard-shell.smoke.mjs` can exercise them without rendering React.

Logout behavior:

- If `authProviderConfig().signOutUrl` is present, show a Logout link/button pointing to that provider sign-out URL. For Better Auth this means `${APP_AUTH_BETTER_AUTH_BASE_URL}/sign-out`; that provider page performs the issuer sign-out flow and returns through the existing local dashboard cleanup route when configured. The local `/auth/betterauth/sign-out?next=...` route remains the stale-cookie/provider-callback cleanup path, not the primary user-initiated Logout target.
- If no external auth provider is configured, show the auth source/provider context but no fake logout operation.
- The Logout control must appear in the sidebar user area and on the Users page so the user page explicitly supports Logout.
- The server route component must thread serializable auth metadata into the client dashboard shell. Metadata includes `source`, `provider`, `cookieName`, `signInUrl`, and `signOutUrl`; the client must not recompute provider environment config.
- The pure logout href selector returns:
  - `null` when `signOutUrl` is null.
  - `signOutUrl` for configured provider flows.
  - The existing local cleanup route is used only by auth redirect/stale-cookie flows already handled outside the visible Logout selector.

## Acceptance Criteria

- `frontend/components.json` exists for the root Next.js app and points shadcn aliases at `frontend/components`, `frontend/lib`, and `frontend/hooks`.
- shadcn-generated imports resolve in the root frontend TypeScript build through `frontend/tsconfig.json` alias support or equivalent relative imports.
- `frontend/components/ui/sidebar.tsx` and supporting shadcn sidebar-08 files/components are present after running shadcn.
- The old dashboard shell is replaced: `DashboardRuntime` no longer renders the custom `Header` plus `SectionNav` single-page navigation as the primary dashboard structure.
- The app has four dashboard pages or route-backed views named Devices, Agents, Users, and Settings.
- The sidebar navigation includes Devices, Agents, Users, and Settings and exposes the active page.
- Users page includes a visible Logout action when a sign-out URL exists.
- No Logout control is rendered when the sign-out URL is null.
- Tenant selection remains available in the new shell when more than one tenant exists.
- Redirects or updated action URLs preserve `tenant`, `command`, and `status` semantics from the current dashboard.
- Existing panels continue to use current data and actions; no backend endpoint is changed.
- Existing i18n files contain labels needed by the new shell in English and Chinese.
- Focused smoke test follows the repo's standalone smoke pattern at `frontend/app/dashboard-shell.smoke.mjs` and is runnable with `node --experimental-transform-types app/dashboard-shell.smoke.mjs` from `frontend/`. It covers the dashboard route/view contract, query preservation, and visible Logout href behavior.
- `npm run build` in `frontend/` succeeds.
- Rust verification required by repo policy is run after code changes: `cargo fmt`, `cargo clippy`, and `cargo nextest run --manifest-path "Cargo.toml" --workspace`. If a command fails for pre-existing or environment reasons, capture the exact failure.

## Safety and Rollback

This is a frontend shell replacement with no database or backend mutation. Rollback is a normal git revert of the dashboard/sidebar commit. The main risk is breaking Next.js build output or auth redirects; targeted smoke tests and `npm run build` are the primary verification for those risks.
